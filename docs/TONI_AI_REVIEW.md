# Методологическая проверка ИИ пояснений

Подготовлен общий текст правил и безопасное форматирование контекста в `analytics/ai_guidance.py`. Модуль экспортирует `SYSTEM_PROMPT`, `TASKS` и `build_prompt(kind, context, question=None)`. Он не вызывает провайдеров, не читает ключи или окружение и не создаёт ответы от имени модели.

Пользователь выбрал проверку без внешних вызовов. Поэтому результат этой работы — review методологии и локальные проверки построения запросов. Реальные ответы Groq или Gemini, качество выполнения инструкций моделью и доступность аккаунтов не проверялись. Демонстрационные входы и сформированные prompts нельзя выдавать за полученные ответы ИИ.

## Проверенные версии

Review выполнен по `origin/frontend/damir` на коммите `03395ef` и `origin/feature/bekzat-p1-infrastructure` на коммите `cfce13d`. Проверены `collab/ai.py`, соответствующие HTTP-адаптеры, frontend-контексты и серверный `collab/context.py` из второй ветки.

В обеих версиях уже есть требования использовать переданные числа, различать null и ноль, писать разницу в п.п., не утверждать причинное преимущество учебника и не оценивать учителей как людей. Также обозначены искусственные данные и правило считать комментарии данными.

## Замечания и изменения методологии

| Наблюдение | Изменение в общей политике | Ограничение проверки |
| --- | --- | --- |
| Нет явного запрета обещать эффект дополнительных часов | План назван предложением; влияние часов на баллы и причинные выводы не утверждаются | Соблюдение моделью требует отдельного live-review |
| Доли 0–1 не отличены от процентов 0–100 | `*_share` и `pair_coverage` переводятся в проценты только для отображения; прирост остаётся в п.п. | Формулы аналитики по-прежнему считает сервер |
| Нет прямого запрета сравнительного вывода при несопоставимых группах | Требуются `comparison_status=comparable` и переданная `difference_gain_pp`; null не восстанавливается из средних | Контекст должен содержать статус и причины ограничения |
| Задание плана всегда описывает переносы | Различаются план на период и перераспределение, рекомендация и ручная правка | Если режим не передан, модель не должна его угадывать |
| Запрет ранжирования учителей допускает неоднозначное толкование | Запрещён рейтинг качества по баллам, приросту или нагрузке; часы описываются как предстоящие часы периода | Организационное описание нагрузки не является оценкой качества преподавания |
| Комментарий может содержать буквальный закрывающий тег `</data>` | `<`, `>` и `&` внутри JSON экранируются; вопрос помещается в отдельный блок с тем же правилом | Это устраняет неоднозначность разметки, но не доказывает устойчивость модели к prompt injection |

Политика также запрещает подменять парную выборку всеми итоговыми результатами, объединять разные версии тестов, приписывать статистическую значимость без расчёта и превращать неполную выборку в автоматическую рекомендацию. Числа в комментариях и вопросах не считаются проверенными метриками.

## Граница отправки данных

В `frontend/damir` HTTP-адаптер передаёт произвольные клиентские `context` и `question` провайдеру. Сводка комментариев включает исходный текст комментариев. Одна инструкция «не использовать персональные данные» не гарантирует, что эти данные не уйдут внешнему сервису: проверка должна произойти на сервере до отправки.

В `feature/bekzat-p1-infrastructure` добавлены серверные селекторы, повторный расчёт агрегатов, ограничение искусственным демонабором и запрет свободного вопроса. ИИ-пояснения `teachers` и `comments` там явно отключены ответом `AI_KIND_NOT_READY`. Эта ветка меняет контракт frontend, поэтому её нельзя считать уже совместимой с произвольными контекстами старого интерфейса.

Фильтр `numbers()` второй ветки удаляет статусы тем, числовые настройки порогов, причины ограничений и режим плана. Для содержательного объяснения следует передавать доверенные enum-статусы, числовые настройки и коды причин вместе с агрегатами. Не требуется разрешать произвольные имена или тексты для восстановления этих полей. Решение о таком контракте и транспортные ограничения остаются отдельной интеграционной работой.

## Подключение общей политики

В нужной версии `collab/ai.py` достаточно добавить импорт:

```python
from analytics.ai_guidance import SYSTEM_PROMPT, TASKS, build_prompt
```

После этого удалить из `collab/ai.py` только дублирующиеся определения этих трёх имён. `json` может оставаться нужен для транспортной сериализации. Сигнатура `build_prompt` одинакова для синхронного адаптера Дамира и асинхронного адаптера Бекзата; provider-код, ключи, настройки, HTTP-маршруты и ограничения доступа эта правка не меняет.

Данный review не копирует весь модуль `collab/` и не подключает внешние вызовы автоматически. Перед объединением необходимо проверить построение контекста целевой ветки и совместимость frontend-контракта.

## Локальные проверки

Аудит проверяет успешный HTTP-ответ, численные значения, сохранение бюджета и неизменность JSON-контекста. Ошибка прекращает выполнение до записи нового отчёта; проверки работают и с `python -O`. В локальном сценарии P0 режим явно передан как `mode="shift"`: строка комментария с `mode=period` его не меняет. Это проверка построения запроса, а не поведения внешней модели. Передачу режима из серверного `collab/context.py` ещё нужно подключить при интеграции.

```powershell
python -m unittest discover -s tests -p "test_ai*.py" -v
```

Проверяются поведение, а не совпадение текста политики с её же копией: вложенные теги в комментариях и вопросе не создают новых границ; JSON восстанавливается без изменения исходных строк, чисел и null; порядок ключей не влияет на prompt; вход не изменяется. Неизвестный вид задачи, неподдерживаемые объекты и неконечные числа завершаются ошибкой до транспорта.

Пять случаев уже подготовлены и проверены на искусственном демонаборе через локальное приложение. Результат сохранён в [артефакте локальной проверки](ai-methodology-offline.json): `prepared_requests=5`, `external_requests=0`, `model_answers_evaluated=0`. Для каждого случая численные проверки и восстановление JSON из блока данных прошли; `model_response=null`, `response_quality_assessed=false`. Это пять подготовленных запросов и ноль внешних вызовов, а не пять ответов модели.

Повторить проверку из корня репозитория в окружении с зависимостями проекта:

```powershell
python -m scripts.audit_ai_methodology --output docs/ai-methodology-offline.json
```

| Случай | Проверенные данные и границы |
| --- | --- |
| `overview_shares` | 120 учеников; доля 0,4 соответствует 40% |
| `comparable_books` | Приросты 16 и 8 п.п.; переданная разность 8 п.п. |
| `limited_comparison` | Недостаточно пар; разность остаётся null |
| `teacher_workload` | 4 учителя, 120 учеников, 30 учеников на учителя, 24 часа на класс |
| `plan_untrusted_comment` | Текущий P0 preview перераспределения с лимитом ±2 и суммой 24 часа; строка с попыткой закрыть `<data>` остаётся внутри JSON |

Последний случай использует существующий режим перераспределения (`shift`), а не новый план на период (`period`). Упоминание периода в общей политике не является проверкой реализации этого режима. Локальный прогон проверяет данные и сформированный запрос; содержание настоящего ответа модели и её устойчивость к вложенным инструкциям здесь не оцениваются.

## Источники конфигурации

Адаптеры читают `GROQ_API_KEY` и `GEMINI_API_KEY` из серверного окружения. Штатный файл деплоя — `deploy/.env`, создаваемый из `deploy/.env.example`; Compose подключает его через `--env-file`. В ветке Бекзата также используются `AI_ENABLED` и `AI_ACCOUNT_VERIFIED`. Значения ключей при этом review не читались и не включались в документы или тесты.

В обеих проверенных версиях default Groq — `openai/gpt-oss-120b`, тогда как переданное P1 ТЗ называет `llama-3.3-70b-versatile`. Этот факт следует учесть при интеграции; методологический модуль не меняет модель и не подтверждает её доступность.
